# Окно в Китай — Controlled Corporate Pilot v1.7.5

## Цель

Проверить продукт в реальной рабочей среде на ограниченной группе сотрудников и получить доказательства бизнес-полезности до расширения внедрения.

Это не HR-инструмент и не система оценки производительности. Usage telemetry используется только для оценки продукта и пилота.

## Wave 1

Целевая группа: **5–10 сотрудников**.

Рекомендуемые функции:

- R&D;
- закупки;
- логистика;
- производство;
- качество;
- 1 представитель руководства или менеджмента.

Стартовать рекомендуется с 3 пользователей в первый день и расширить до 5–10 после подтверждения технической стабильности.

## Приватность

В Pilot Control Room не сохраняются и не отображаются имя и email участника.

Идентификация для KPI:

- SSO-пользователь или локальное pilot-device преобразуется существующим HMAC-механизмом в `user_key`;
- в отчёте показывается только псевдоним вида `P-ABC123`;
- персонального Watchlist нет;
- KPI не используются для оценки эффективности сотрудника.

В `AUTH_MODE=proxy` feedback API принимает данные только от доверенной корпоративной identity chain.

## Pilot Control Room

Маршрут: `/pilot`.

В local/demo режиме `PILOT_CONTROL_MIN_ROLE=viewer`. Для controlled corporate pilot рекомендуется:

```env
AUTH_MODE=proxy
PILOT_CONTROL_MIN_ROLE=admin
EXECUTIVE_MIN_ROLE=editor
```

Control Room показывает:

- фактическое число пользователей продукта;
- repeat usage;
- feedback respondents;
- полезность;
- оценённое пользователями сэкономленное время;
- просмотры Truck Radar / Decision Cockpit / Executive Brief;
- S1–S4 issues;
- текущий итог `GO / ADJUST / STOP`.

Служебные страницы `/admin`, `/pilot` и `/pilot-feedback` не увеличивают размер cohort. Пользователь считается участником только после посещения рабочих разделов продукта.

## Feedback

Маршрут: `/pilot-feedback`.

Форма спрашивает:

- рабочую функцию;
- что произошло: полезный сигнал / экономия времени / помощь решению / замечание к данным / проблема / отсутствие пользы;
- общую оценку 1–5;
- практическую полезность 1–5;
- приблизительно сэкономленные минуты;
- раздел продукта;
- короткий комментарий.

Имя и email форма не запрашивает и в `pilot_feedback` не хранит.

## KPI по умолчанию

| KPI | Default gate |
|---|---:|
| Evaluation window | 10 дней |
| Cohort | 5–10 пользователей |
| Repeat usage | ≥ 40% |
| Feedback respondents | ≥ 3 |
| Полезность (оценка 4–5) | ≥ 70% |
| Open S1 | 0 для продолжения |
| Open S2 | 0 для чистого GO |

Пороговые значения меняются только через environment policy:

```env
PILOT_WINDOW_DAYS=10
PILOT_TARGET_MIN_USERS=5
PILOT_TARGET_MAX_USERS=10
PILOT_MIN_FEEDBACK=3
PILOT_MIN_USEFUL_PCT=70
PILOT_MIN_REPEAT_PCT=40
```

## Severity

### S1 — Critical

Пример: сервис недоступен группе, потеря/повреждение данных, критическая security-проблема, систематически неверные decision-critical данные.

Любой открытый S1 → `STOP`.

### S2 — Major

Пример: важный раздел не работает, существенный источник или бизнес-логика дают неверный результат, проблема блокирует нормальный сценарий пилота.

- 1 open S2 → `ADJUST`;
- 2+ open S2 → `STOP`.

### S3 — Minor

Неблокирующая функциональная или UX-проблема. Обычно не останавливает пилот.

### S4 — Improvement

Пожелание или улучшение без дефекта критического сценария.

## Outcome engine

### GO

- v1.7.4 operational gate не `NO_GO`;
- cohort в диапазоне;
- repeat KPI достигнут;
- feedback достаточно;
- usefulness KPI достигнут;
- нет open S1/S2.

### ADJUST

Пилот технически можно продолжать, но до расширения нужна корректировка. Например:

- меньше 5 или больше 10 участников;
- мало feedback;
- repeat usage ниже цели;
- usefulness ниже цели;
- один open S2.

### STOP

- operational gate `NO_GO`;
- любой open S1;
- два и более open S2.

`STOP` означает остановить расширение и исправить причину. Он не означает автоматически закрыть проект.

## Реальный сценарий запуска

### Day 0 — IT

1. Развернуть сервис через существующий one-click/Docker процесс.
2. Проверить `/api/health` и `/api/ready`.
3. Выполнить:

```bash
npm run pilot:go-no-go
```

4. Для корпоративного режима проверить SSO/RBAC.
5. Убедиться, что Executive Brief показывает приемлемый freshness status.

### Day 1 — 3 пользователя

Дать короткое задание без искусственного тестового сценария:

- открыть новости;
- проверить интересующие темы;
- использовать Truck Radar или Decision Cockpit, если относится к работе;
- дать feedback только по реально возникшему полезному кейсу или проблеме.

### Day 2–3 — 5–10 пользователей

Если нет S1/S2, расширить до полной Wave 1.

### Day 5 — Midpoint review

Проверить:

- cohort;
- repeat usage;
- топ используемых рабочих разделов;
- feedback;
- S1–S4;
- source/data quality;
- реальные примеры экономии времени или найденных сигналов.

### Day 10 — Final review

Открыть `/pilot` и зафиксировать `GO / ADJUST / STOP` вместе с причинами.

После запущенного instance IT может получить итог в CLI:

```bash
npm run pilot:outcome
```

При `STOP` команда возвращает non-zero exit code. `ADJUST` не считается аварийным CI-failure: это бизнес-решение продолжить пилот с корректирующими действиями.

## Что считать успехом

Основной KPI не page views. Успех — когда сотрудники могут показать хотя бы несколько конкретных случаев, где сервис:

- раньше заметил значимый отраслевой сигнал;
- сократил ручной поиск по множеству источников;
- помог подготовить обсуждение/решение;
- дал полезный China/Russia или truck-market контекст.

Количество кликов используется только как вспомогательный показатель принятия продукта.
